# Design

## Context

See proposal.md. The backend is complete for auth and projects: `POST /auth/register|login|refresh|logout`, `GET /auth/me`, and `/projects` (create, list with `includeArchived`, get with `role`, patch, archive, members list, add by email, remove). The refresh cookie is `refresh_token`, httpOnly, Secure, SameSite=Strict, path `/api/v1/auth`. Shared schemas exist in `packages/shared` (`auth.ts`, `projects.ts`, `common.ts`, `ErrorResponseSchema`). `frontend/` is a stub (`src/index.ts`, Vitest 5.0.5, TypeScript 6.0.3). Context7 was used for Vite 8 (`server.proxy`, `preview.proxy`), React Router (`createBrowserRouter`, `Outlet`), shadcn (Vite install, Tailwind v4 `components.json`, `@/` alias) and TanStack Query v5. Context7 had no React Router 8 material (only 7.x), so the 8.5.1 usage follows the official React Router docs (limitation noted; same data-router API). Versions were read from the npm registry on 2026-11-01.

## Goals / Non-Goals

**Goals:** FR-FE-1, 2, 3, 8, 9, 10; Lighthouse 95+ on login and project list on the production build; a shell DEV-1012 can build on without editing Group 1 files.

**Non-Goals:** task pages, Playwright, dark mode, i18n, backend changes.

## Decisions

1. **Group 1 is the frontend contract.** It exposes `src/lib/api/client.ts` (`apiFetch`), `src/lib/auth/` (`AuthProvider`, `useAuth`, in-memory token), `src/components/ui/*` (shadcn), `src/components/states.tsx` (`LoadingState`, `EmptyState`, `ErrorState`), `src/routes/router.tsx` with `ProtectedRoute` and `AppLayout`, a `src/test/` render helper, and `scripts/lighthouse.mjs`. DEV-1012 only adds routes, pages and a Lighthouse page entry.
2. **Packages (exact, pinned, need Gate 1 approval).**
   - Frontend runtime: `react` 19.3.1, `react-dom` 19.3.1, `react-router` 8.5.1, `@tanstack/react-query` 5.105.1, `@team-task-tracker/shared` (workspace), `zod` 4.6.7 (already pinned in shared), `class-variance-authority` 0.7.1, `clsx` 2.1.1, `tailwind-merge` 3.7.0, `lucide-react` 1.66.0, `@radix-ui/react-slot` 1.5.0, `@radix-ui/react-label` 2.1.17, `@radix-ui/react-dialog` 1.3.1.
   - Frontend dev: `vite` 8.3.5, `@vitejs/plugin-react` 6.1.2, `tailwindcss` 4.3.3, `@tailwindcss/vite` 4.3.3, `@types/react` 19.3.0, `@types/react-dom` 19.3.0, `jsdom` 30.1.3, `@testing-library/react` 16.3.3, `@testing-library/dom` 10.4.2, `@testing-library/user-event` 14.6.8, `@testing-library/jest-dom` 7.0.1.
   - Root dev (Lighthouse script): `lighthouse` 13.6.0, `chrome-launcher` 1.2.2.
   - The `shadcn` CLI is not installed: component sources are copied into `src/components/ui` by hand (they are source, not a dependency), which avoids an extra package and an unpinned `npx`.
   - `react-router` is the one addition outside the original stack list. All packages go into `docs/VERSIONS.md`.
   - `@tanstack/react-query` and `lucide-react` were published within two days of this proposal. If pnpm's release-age policy blocks one, the install uses the previous patch and the table is updated; no new `minimumReleaseAgeExclude` without asking.
3. **Same origin through a proxy.** `vite.config.ts` sets `server.proxy` and `preview.proxy` for `/api` to `BACKEND_URL` (default `http://localhost:3000`, from the process environment). The client always calls relative `/api/v1/...`, so the cookie path matches and there is no CORS. The Secure cookie works on `http://localhost` in Chrome, Edge and Firefox.
4. **API client.** `apiFetch` sends `Authorization: Bearer <memory token>` and `credentials: 'same-origin'`, parses success bodies with the shared response schema and error bodies with `ErrorResponseSchema` into an `ApiError { status, code, message, details }`. On a 401 from a non-auth path it calls `POST /auth/refresh` once (one shared in-flight promise for concurrent calls), retries the original request once, and on refresh failure clears the token and signals logout. `/auth/*` calls are never retried. No generated client: one function per route in `src/lib/api/auth.ts` and `projects.ts`.
5. **Token and session.** The access token lives in a module variable plus `AuthProvider` state, never in localStorage or sessionStorage. On load `AuthProvider` calls refresh (status `loading`, then `authenticated` with the user from `GET /auth/me`, or `anonymous`). Logout calls `POST /auth/logout`, clears the token and the TanStack Query cache.
6. **Console-clean first load (Lighthouse risk).** A refresh that returns 401 for an anonymous visitor is logged by Chrome as a console error, which lowers Best Practices on the login page. Mitigation: a non-secret flag `ttt.session=1` in `localStorage` (not a token) is set on login or register and cleared on logout or a failed refresh; without it the load-time refresh is skipped and the user is `anonymous` immediately. A stale flag costs one failed refresh that clears it. If the Lighthouse run shows the flag is unnecessary, task 1.4 may drop it and record a deviation.
7. **Routing and guard.** `createBrowserRouter`: public `/login` and `/register`; a protected `AppLayout` route wrapping `/projects` and `/projects/:projectId`; `/` redirects to `/projects`; unknown paths render a not-found page. `ProtectedRoute` shows `LoadingState` while the session is `loading`, redirects to `/login` (original location in router state) when `anonymous`, and renders `Outlet` otherwise. Login and register redirect authenticated users to `/projects`. Page routes use `lazy` so the login page ships a small bundle.
8. **Server state.** TanStack Query: `useQuery` for list, detail and members; `useMutation` for create, update, archive, add and remove member, with `invalidateQueries` on success. Keys: `['projects', { page, pageSize, includeArchived }]`, `['project', id]`, `['project', id, 'members']`. Forms validate with the shared schemas via `safeParse` (`RegisterRequestSchema`, `LoginRequestSchema`, `CreateProjectRequestSchema`, `UpdateProjectRequestSchema`, `AddMemberRequestSchema`); no form library. Server 400 `details` are shown next to fields when present.
9. **Permissions in the UI (SDS section 6).** The project detail response carries `role`. An OWNER sees edit, archive, add member and remove member; a MEMBER sees none of them (hidden, not disabled; the member list is read-only). Archived projects hide all write actions for every role. Any authenticated user sees "New project". The backend still enforces 403 and the UI maps a 403 to an `ErrorState`.
10. **Error and state mapping.** 401 after a failed refresh: redirect to login. 403: "You do not have permission". 404: "Not found" (non-members and unknown projects look the same). 409 `LAST_OWNER`: inline "A project needs at least one owner" on the members list, list unchanged. 409 `PROJECT_ARCHIVED`: inline message. 409 on adding an existing member: inline message. Network failure: `ErrorState` with retry. Empty list: `EmptyState` with a create action. Each data view has loading, empty and error states.
11. **Pagination.** The project list uses `?page&pageSize=20&includeArchived`, with previous and next controls from `meta.totalPages`; state is kept in URL search params.
12. **Styling and accessibility.** Tailwind v4 via `@tailwindcss/vite`, tokens as CSS variables in `src/index.css`, copied shadcn components (`button`, `input`, `label`, `card`, `dialog`, `alert`, `badge`, `skeleton`). Every input has a label, headings are ordered, contrast meets AA. `index.html` has `lang`, a `title`, a meta description and a viewport meta. System fonts and no images, to keep Performance high.
13. **Lighthouse gate.** `scripts/lighthouse.mjs` runs the frontend production build, starts a small stub API on a free port (Node `http`; serves `/api/v1/auth/refresh`, `/auth/me` and `/projects` fixtures, no database), starts `vite preview` with its proxy pointed at the stub, launches Chrome through `chrome-launcher`, runs Lighthouse (default config) on `/login` and `/projects`, prints the four category scores per page and exits 1 if any is below 95. The browser comes from `CHROME_PATH` or an installed Chrome or Edge; if none is found it fails with a clear message. Pages are an array so DEV-1012 appends the task list. CI does not run it in this ticket (needs a browser, slow); it is a documented local gate, recorded as a deviation.
14. **Tests.** Vitest + jsdom + Testing Library. API client unit tests with a mocked `fetch` (refresh once, no loop, error parsing, token never written to storage). Component tests for forms (validation, submit, server error) and permission states (OWNER, MEMBER, archived). No tests of docs, evidence or styling.
15. **Scripts and build.** Frontend scripts: `dev` (`vite`), `build` (`tsc --noEmit` then `vite build`), `preview`, `typecheck`, `test` (`vitest run`). The frontend `tsconfig` uses `moduleResolution: bundler`, `jsx: react-jsx`, DOM `lib`, `types: [vite/client]`, `noEmit` and the `@/` alias. `packages/shared` must be built first, as for the backend today.

## Risks / Trade-offs

- **Secure cookie and Safari.** Safari does not send Secure cookies on `http://localhost`, so local session persistence may fail there. Documented; Chrome, Edge and Firefox are the supported dev browsers.
- **Lighthouse flakiness and browser dependency.** Scores vary by machine; reaching 95 may need preview-server tuning (compression, cache headers). Task 1.4 includes fixing what the run reports. A machine without Chrome or Edge cannot run it.
- **Stub API in the Lighthouse script** audits the real UI against fixtures, not the real backend; end-to-end coverage is DEV-1016.
- **New router dependency and fresh versions** are the main Gate 1 questions (decision 2).
- **Parallel work with DEV-1012.** Both touch `router.tsx` and `package.json`; conflicts are limited to one route array and dependency lines, and Group 1 merges first.
