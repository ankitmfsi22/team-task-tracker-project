### Checked, no issue

- **Layering:** routes only wire middleware, controllers only parse and delegate, and all business logic is in services. The `controller.list` re-parse of the query (D-058, D-073, D-083) is the only schema use in controllers and is accepted.
- **Membership and role checks:** `projectAccess` (`middleware/project-access.ts:20-48`) returns 404 for a non-member or missing project (indistinguishable bodies), then 403 for a role failure, then 409 for a write to an archived project, in the order the spec requires. Every project-scoped route in `projects.routes.ts`, `tasks.routes.ts`, `comments.routes.ts` and `activity.routes.ts` uses it.
- **Cross-project leakage:** every task, comment and activity lookup is scoped by `{ id, projectId }` or `{ id, taskId }`, so a task from another project returns 404.
- **Zod validation:** every route validates body, params or query with `packages/shared` schemas. The task, comment and add-member bodies and the comment list query are strict, so unknown fields return 400. Frontend `zod` use only parses API responses or builds a small date-input regex (`frontend/src/lib/api/task-list-params.ts:25`). Backend `zod` use is a type import only. No domain schema is redefined outside shared.
- **Code rules:**
  - No `any`, `@ts-ignore` or `@ts-expect-error` in `backend/src`, `frontend/src`, `packages/shared/src`, `e2e` or `scripts` (excluding `scripts/tests` and generated Prisma).
  - The only `eslint-disable` is `middleware/error-handler.ts:20`, and it carries DEV-1006.
  - The `as ActivityResponse` cast in `services/activity.service.ts` is D-082.
- **Atomicity:** assign, status change, archive and create write the task change and the activity entry in one transaction. Failure tests are at `tasks.activity.integration.test.ts:243` and `:260`.
- **Last-owner rule:** removal runs in a serializable transaction (`services/projects.service.ts:134-148`) and is tested at `projects.members.integration.test.ts:260`.
- **Spec scenarios for projects, tasks, comments and activity:** each has an implementation and a named test. Covered cases include the due-date rule, assignee membership, status transitions, task archive, comment 403 and 404 cases, activity append-only, trimming, archived task and archived project 409s, and the invalid filter, sort and pagination 400s.
- **Auth and secrets:**
  - The refresh cookie is httpOnly, secure and sameSite strict, scoped to `/api/v1/auth`.
  - Refresh tokens are stored hashed and rotated by a conditional revoke.
  - Responses contain no `passwordHash`; `toUser` returns only id, email and name.
  - The error handler returns 500 with no internals.
  - The only console output in `backend/src` is `main.ts:7` and `main.ts:9` (port and startup error message).
  - The frontend keeps the access token in a module variable (`frontend/src/lib/auth/token.ts`). `localStorage` holds only a session hint flag (`frontend/src/lib/auth/auth-context.tsx:30-39`).
- **Frontend permissions:** `frontend/src/lib/comment-permissions.ts` mirrors the backend rule (author edits, author or OWNER deletes) and is documented as a UI affordance only. The scenario map, checked by script, lists web 403, 404 and MEMBER read-only tests such as `project-detail.test.tsx` and `task-list-states.test.tsx`. I did not open every frontend test file.
